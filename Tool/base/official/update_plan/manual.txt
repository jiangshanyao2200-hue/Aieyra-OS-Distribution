Records an editable, persistent Plan or Goal for the current task. This tool cannot read files, run commands, or independently verify work. At a host-confirmed new user task boundary, new_task=true with creation or the snapshot form archives the previous plan unchanged; never use it to bypass unfinished acceptance for the same task. Continuations update the existing plan. Compatibility snapshot form: summary plus plan:[{id?,description,status,result?}] (no action). New snapshots use step descriptions as explicit acceptance criteria; existing snapshots must retain IDs/order/text. Every newly completed step requires actual observations in result; all completed snapshots perform acceptance atomically. Structural edits or separately defined acceptance require the full form below. Simple creation: action=create, objective, acceptance, steps:[{text,status?}]; mode defaults to plan, IDs are assigned and returned, status defaults to pending. Full creation: expected_revision=0, mode=todo/plan (one phase P) or phase/goal (1-32 phases with stable alphanumeric, underscore or dash IDs), objective, acceptance criteria, and steps (stable unique IDs, pending/in_progress). First call displays the whole plan. Updates may omit expected_revision: it binds to the snapshot at model request start, never a newer execution-time state. Use one atomic update per response; subsequent omitted revisions in that same response may conflict. Explicit expected_revision remains supported. plan_id is optional when targeting the current plan; if supplied it must match. Send atomic changes: revise(step_id,text); insert(phase_id,new_step,before_id/after_id); replace(step_id,new_step with a NEW unique id; use revise for text-only changes); set_status(step_id,status,evidence/resume_condition); move(step_id,phase_id,before_id/after_id); phase_add(phase_id,title,steps); phase_revise(phase_id,title); set_lifecycle(status=active/paused/blocked/cancelled). REQUIRED for every change: either provide a top-level reason applying to the whole batch, or put reason on EVERY change (including set_status). A reason on one change does not cover its siblings. step_id/before_id/after_id accept stable IDs or unique exact step text; ambiguity returns candidate IDs. Common status aliases running/done/todo/canceled are accepted. Keep at most one in_progress and at most 512 total steps. Steps may declare depends_on:[stable step IDs], requiring ALL dependencies completed before starting or completing; pending dependent steps are skipped when choosing current work. Update dependencies using set_dependencies(step_id,depends_on). Cycles, missing references and false completion reject the whole atomic batch. Replacement redirects dependencies to the new step. A blocked step does not block independent work: keep the goal active and continue runnable steps; set the entire goal blocked only when no runnable work remains. Explicit user pauses stay paused. Completed steps require factual evidence; deferred steps require resume_condition={step_id,status:"completed"} or {detail:"condition"}. A completed prerequisite returns deferred work to pending. Cancelled/replaced work is NOT completed. Text revisions retain old and new text. Do not change the objective/acceptance criteria to make completion easier. Finish with action=complete and completion:[{criterion:exact acceptance text,evidence:[facts]}] for every criterion, after all remaining steps complete. You may include final set_status completed changes with evidence in the same complete call; final changes and acceptance commit together or all reject. Other edits must use update. Missing prerequisites can be recorded in blocked steps and their resume conditions. A repeated request that leaves state unchanged returns ok=true,no_change=true with the current state: this is success, do not retry it or spend further calls changing only the reason. On revision_conflict use returned latest state. Highest known revision is authoritative across Compact.
